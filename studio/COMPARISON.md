# Comparison and synthesis record

## Executive judgment

The first 2.0 package is the stronger **design practice**: it has broader specialist depth, better architecture guidance, more mature client partnership, richer evidence templates and clearer cross-platform quality gates.

The second 2.0 package is the stronger **execution harness**: it turns briefs into work orders, models decisions, validates ownership, claims paths, scaffolds modules and runs local gates with no package installation.

Design Harness 3.0 uses the first as its practice standard and the second as its executable spine.

## Comparison

| Dimension | First package | Second package | 3.0 decision |
|---|---|---|---|
| Studio model | Modular coordinator plus 28 broad profiles | Director/Producer stage model with 27 strict roles | Keep director/producer authority; route the smallest team from a broad roster |
| Client relationship | Detailed partnership practices and templates | Strong single Engagement Lead and one-question intake | Keep both: one relationship owner plus evidence-based client-care practices |
| Design systems | Strong token hierarchy, platform adaptation and consumer review | Executable token stub and token lint | Combine the complete system model with executable stubs, lint and versioning |
| Product architecture | Clear contracts/domain/capability/UI/adapter/shell layers | Module manifests, graph checks and scaffold utility | Keep both; manifests operationalize the architecture |
| Parallel work | Conservative wave planner and ownership guidance | Work orders, claims, TTLs, overlap/cycle detection | Use work orders and claims; retain the caveat that file claims are not distributed locks |
| Decision memory | ADR and evidence templates | Design Decision Model with loopbacks and export | Use the DDM for product/design decisions and ADRs for technical decisions |
| Platform coverage | iPhone, iPad, web plus domain-rich profiles | iOS, iPadOS, macOS-adjacent, immersive/SaaS/editorial web | Preserve all listed platforms and add dedicated macOS guidance |
| Domain coverage | Music, art, CMS/content, marketing, editorial and SaaS | Similar domains with sharper output ownership | Keep the sharper role contracts and add missing risk specialists |
| Quality | Nuanced human gates and evidence limits | Runnable gate command and verifier role | Require human review and mechanical checks; neither substitutes for the other |
| Prototyping | Dedicated prototype specialist | Identified as a future gap | Make prototyping a first-class optional stage |
| Security/performance/integration | Dedicated specialists | Mostly distributed across architects/engineers | Restore these as conditional risk roles |
| Runtime portability | Runtime-neutral layout | Runtime-specific agent location | Canonical `agents/` plus small runtime entry files |
| Dependencies | Python and Node examples; no downloads | Node standard library only | Standardize core utilities on Node only; no network or package install |
| Risk | More documentation than execution | More executable, but rigid default plan and lenient empty gates | Keep executable core while making stage selection proportional and empty evidence explicit |

## What was deliberately removed or reduced

- Duplicate role descriptions that differed mainly in naming.
- The idea that every project needs every specialist or every stage.
- Framework-specific prescriptions before the brief establishes need.
- Claims that scripts enforce real distributed locks or prove product quality.
- Remote source links, remote prompts, CDNs and third-party runtime dependencies.
- Pixel parity across platforms; shared semantics with native adaptation is the standard.
- Speculative metrics presented as facts. Budgets remain hypotheses until measured.

## Forward-looking additions

- AI Experience & Trust specialist for agentic workflows, preview/approval, provenance, uncertainty, undo and audit.
- Interaction Prototyper for high-risk behavior before expensive platform implementation.
- Security & Privacy, Performance & Resilience and Integration specialists as conditional risk lanes.
- Data Visualization and Localization specialists for dense products and global delivery.
- A complete design-system standard covering foundations through governance and migration.
- macOS-specific guidance instead of treating it only as a large iPad.

## Practical default team

Most engagements should begin with five to eight roles, not the full roster:

1. Engagement Lead
2. Studio Director
3. UX Researcher or Information Architect
4. One platform specialist
5. One domain specialist
6. Design Systems Engineer
7. Relevant engineer or prototyper
8. Verifier, with conditional accessibility, security and performance review

Expand only when a distinct risk, artifact or decision needs a distinct owner.
